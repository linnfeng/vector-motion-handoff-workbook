# Vector Motion Handoff Workbook

This workbook is a practical document for reviewing an animated vector asset before another person embeds, revises or exports it. It provides questions and reusable handoff fields, not a software package or an automated accessibility test. The aim is to make the next decision understandable without requiring the next reviewer to reconstruct every experiment that came before it.

I am associated with SVG Animation, and this document was prepared with AI assistance. For a browser-based starting point, see [svg animation](https://svganimation.app/). That project describes importing vector artwork, working with presets or AI, retaining editable source and exporting SVG, GIF or MP4. Its inclusion is a disclosed project reference, not an independent endorsement or a claim that every workflow below has been tested against every destination.

## Start with the communication job

Before choosing an effect, write what the movement should help somebody notice. A loading symbol, a logo introduction and an explanatory diagram have different jobs even when they share similar shapes. Describe the intended observation in a short sentence. If the sentence only says that the asset should look exciting, narrow it until somebody else could tell whether the important detail remains visible.

Separate the purpose from a preferred technique. A reviewer can agree that a selected item should stand out while disagreeing that it needs to spin. This distinction protects the useful part of the brief when a particular animation causes a distraction. Record the audience, placement and expected viewing duration as assumptions rather than pretending that they are measured facts about every future visitor.

## Preserve a recognizable starting point

Keep an identifiable source version before making a revision. A thumbnail alone cannot explain which paths, text or colors remain editable, and a downloaded video is not a substitute for the vector source. Give the source a descriptive name and preserve the relationship between that name and the exported file. Do not rely on a filename such as final to carry the entire history of the work.

The starting point should be something the reviewer can recognize. Explain which elements are intentionally unchanged and which are open to discussion. If an AI-assisted operation is involved, preserve the accepted source before requesting the next change. A revised composition that looks attractive may still have lost an important detail. Keeping a known reference makes that loss easier to discuss without relying on memory.

## Describe movement before judging polish

Review the beginning, middle and end of a sequence separately. Identify the resting frame, the moment that draws attention and the point at which the asset returns or stops. A loop can appear smooth during casual playback while still having an abrupt join. Slow observation helps isolate the join from other questions such as color, scale or overall preference.

Use concrete descriptions when possible. Instead of saying that the movement feels wrong, explain that the label disappears before the related shape arrives or that the object reverses direction unexpectedly. Such comments identify a decision that can be revised. They do not require a reviewer to claim expertise in animation software, and they avoid turning a shared review into a contest over vague adjectives.

## Keep timing attached to its context

Record the intended duration and whether the asset should repeat. A short decorative loop in a small card is not automatically suitable as a large presentation background. Changing the scale or placement can change how noticeable the same movement becomes. Describe the proposed placement and leave room for the implementer to verify the actual result there.

Avoid treating a preferred preview speed as a universal answer. Consider whether somebody arrives halfway through a loop, whether the important information remains available after it ends and whether repeating it adds meaning. If those questions remain unresolved, include them in the handoff instead of silently replacing uncertainty with a confident approval. Clear open questions are often more useful than a broad statement that everything looks good.

## Review the still experience as well

A motion asset should have an understandable still state when its purpose requires one. Check what remains visible when playback is paused, blocked or intentionally reduced. The appropriate alternative depends on the placement and content. A decorative mark may need a different treatment from a diagram that conveys an instruction through movement.

This workbook is not a compliance certificate. Ask the person integrating the asset how reduced-motion preferences and other accessibility requirements will be handled in the real page. Review contrast, text readability and the ability to understand important information without following a rapid sequence. A friendly preview does not establish that every embedding method respects the same settings or exposes equivalent information.

## Choose a delivery format deliberately

Choose an export because the destination accepts it, not because it was the first download option. SVG keeps vector markup available for supported placements. GIF can serve a repeating-image placement, while MP4 fits a video-oriented destination. Those general distinctions are useful starting points, but actual behavior depends on the file and the system that displays it.

Write down the requested dimensions, background treatment and intended duration with the chosen format. Check the downloaded artifact independently of the editor preview. A file that opens successfully in one viewer may still behave differently after a content system resizes it or changes how it is embedded. Do not promise identical rendering everywhere merely because one local observation looked correct.

## Make AI revisions specific and bounded

When asking for an AI-assisted revision, state what should remain unchanged along with the desired adjustment. A request to change one color should not implicitly invite a new composition. Identify the subject, the property to change and the constraints that matter. Then compare the returned source with the accepted version before replacing it in the working collection.

Treat the result as a proposal rather than evidence that the request was understood perfectly. Look for accidental changes in text, proportions, layer relationships and motion. Avoid claims about improved performance or conversion unless a separate measurement supports them. The useful question during this review is whether the new artifact satisfies the stated visual brief while preserving the parts that were already accepted.

## Use a compact handoff record

A handoff record should reduce repeated explanation. Capture the source identifier, delivery filename, intended placement, requested format and remaining checks. Add the reason for any unusual choice. The next person should be able to distinguish an intentional compromise from a detail nobody has reviewed yet, without guessing which conversation contains the authoritative answer.

| Field | Fill in for this asset |
| --- | --- |
| Communication job | What the movement helps somebody notice |
| Accepted source | Descriptive source name and revision |
| Delivery | Export filename, format and dimensions |
| Playback | Duration, repeat behavior and resting frame |
| Alternative | Still or reduced-motion approach to confirm |
| Open question | Unresolved issue and person checking it |

Use the table as a starting template, not as proof of completed testing. Blank fields should remain visible until somebody can answer them. If a decision changes, update the record together with the relevant artifact. A perfectly formatted table attached to an obsolete export creates more confusion than a short, accurate note beside the current file.

## Separate observations from conclusions

An observation describes what somebody actually saw: a label was readable at a particular size, a loop restarted abruptly or a downloaded file opened in a named viewer. A conclusion explains what that observation means for the next decision. Keeping the two separate prevents a small successful check from becoming an unsupported statement about every browser, audience or device.

Record unresolved differences without hiding them behind a single approval label. One reviewer may have assessed appearance while another checked the file in its intended placement. Their approvals cover different scopes. State those scopes plainly, preserve the accepted source and leave the remaining checks to the people who can actually perform them. That is the central purpose of this workbook.
